- [ ] **Step 1.4 — Add the `XpEvent` model**

```prisma
model XpEvent {
  id        String   @id @default(cuid())
  garageId  String
  delta     Int
  reason    XpReason
  sourceRef String?  @db.VarChar(120)
  createdAt DateTime @default(now())

  garage Garage @relation(fields: [garageId], references: [id], onDelete: Cascade)

  @@unique([garageId, reason, sourceRef])
  @@index([garageId, createdAt])
}
```

Notes for the engineer:

- `delta Int` is signed at the DB layer. `admin_adjustment` is the only reason allowed to insert negative deltas (§C8); the awarder enforces. Schema stays permissive.
- `sourceRef` is **nullable** at the DB level for migration-compat / schema flexibility, **but the awarder boundary enforces non-null** (canon §7). Every awarder write (`awardXp`, chunk 27) and every admin-route write (chunk 35, UUID-suffixed sourceRef) MUST supply a non-null `sourceRef`. Postgres treats `NULL` as distinct in unique indexes, so the `@@unique([garageId, reason, sourceRef])` only enforces idempotency when `sourceRef` is non-null — that's acceptable precisely because the awarder layer enforces non-null at the call boundary. Do NOT rely on schema-level NULL for any production write path (overrides outline §C1 / §C7 ambiguity).
- The single `@@unique([garageId, reason, sourceRef])` **replaces** the outline §353 plain `@@index([garageId, reason, sourceRef])`. A unique index is also a usable index for lookups — no separate `@@index` needed for the revert-path findUnique in §C2.
- `@@index([garageId, createdAt])` powers per-garage chronological audit listing (DSR export + future admin debug view).
- `onDelete: Cascade` from Garage matches the existing `GarageBadge` cascade pattern. **LGPD/DSR implication:** when a user is anonymized or deleted, removing the user's `Garage` row triggers `ON DELETE CASCADE` and physically wipes every `XpEvent` for that garage in the same transaction. Chunk 28's DSR anonymize service relies on this — it does not need a separate `xpEvent.deleteMany` if it deletes the Garage, but the canonical anonymize path keeps the Garage row and resets counters + explicitly `prisma.xpEvent.deleteMany({ where: { garage: { userId } } })`. Either way, cascade is the safety net.

**Schema rationale — counters + audit (canon §14):**

- `Garage.xp` is the **authoritative running balance**. It is the sum of every `XpEvent.delta` for the garage, maintained by the awarder in the same transaction as the `XpEvent` insert. Reads (progress endpoint, scoreboard UI) hit the column directly — never `SUM(delta)` from `XpEvent`.
- `Garage.likesReceived` is a **denormalized counter** owned by the awarder (canon §6). `awardXp('post_like', …)` increments `xp` AND `likesReceived` in one `prisma.garage.update`; `revertLikeXp` decrements both in one statement. Route handlers (chunk 32) MUST NOT touch `likesReceived` directly. The denormalization avoids an aggregate query on every garage read and keeps the public stats payload O(1).
- `XpEvent` is the **append-only audit trail**. Every accrual writes a row; reverts (unlike) write a row with negative delta (per §C2). The trail powers DSR export (chunk 28 surfaces these rows in the export payload), admin debugging, and forensic reconciliation if the running balance ever drifts.

```sql
-- CreateEnum
CREATE TYPE "XpReason" AS ENUM ('event_checkin', 'car_create', 'post_create', 'post_like', 'badge_award', 'premium_activation', 'admin_adjustment');

-- AlterTable
ALTER TABLE "Garage" ADD COLUMN     "likesReceived" INTEGER NOT NULL DEFAULT 0,
ADD COLUMN     "xp" INTEGER NOT NULL DEFAULT 0;

-- CreateTable
CREATE TABLE "XpEvent" (
    "id" TEXT NOT NULL,
    "garageId" TEXT NOT NULL,
    "delta" INTEGER NOT NULL,
    "reason" "XpReason" NOT NULL,
    "sourceRef" VARCHAR(120),
    "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,

    CONSTRAINT "XpEvent_pkey" PRIMARY KEY ("id")
);

-- CreateIndex
CREATE INDEX "XpEvent_garageId_createdAt_idx" ON "XpEvent"("garageId", "createdAt");

-- CreateIndex
CREATE UNIQUE INDEX "XpEvent_garageId_reason_sourceRef_key" ON "XpEvent"("garageId", "reason", "sourceRef");

-- AddForeignKey
ALTER TABLE "XpEvent" ADD CONSTRAINT "XpEvent_garageId_fkey" FOREIGN KEY ("garageId") REFERENCES "Garage"("id") ON DELETE CASCADE ON UPDATE CASCADE;

Prisma's generator produces ALTER-TABLE before CREATE-TABLE within the same migration, which is fine — both happen in one transaction and there's no ordering dependency between the Garage columns and the XpEvent table beyond both depending on the enum being created first. The enum is created first (line 2), satisfying the constraint.

If Prisma alphabetizes the two new `Garage` columns (`likesReceived` before `xp`), accept it. The schema source order (`xp` before `likesReceived`) does not need to match the migration's `ADD COLUMN` order — they're independent statements.

- [ ] **Step 3.1 — Write the failing test**

```ts
// apps/api/test/garage/xp-schema.test.ts
import type { XpReason } from '@prisma/client';
import { prisma } from '@jdm/db';
import { afterEach, beforeEach, describe, expect, it } from 'vitest';

import { createUser, resetDatabase } from '../helpers.js';

// `createUser()` already mints a Garage for the user (signup-hook + migration
// backfill invariant; see helpers.ts). `Garage.userId` is unique, so tests
// MUST reuse that garage via `findUniqueOrThrow({ where: { userId } })`
// instead of calling `prisma.garage.create()` a second time (P2002).
const garageFor = (userId: string) => prisma.garage.findUniqueOrThrow({ where: { userId } });

describe('schema: Garage XP columns + XpEvent table (chunk 23)', () => {
  beforeEach(async () => {
    await resetDatabase();
  });
  afterEach(async () => {
    await resetDatabase();
  });

  it('defaults Garage.xp and Garage.likesReceived to 0 on insert', async () => {
    const { user } = await createUser({ email: 'xp1@jdm.test' });
    const garage = await garageFor(user.id);
    expect(garage.xp).toBe(0);
    expect(garage.likesReceived).toBe(0);
  });

  it('persists xp + likesReceived increments atomically', async () => {
    const { user } = await createUser({ email: 'xp2@jdm.test' });
    const garage = await garageFor(user.id);
    const updated = await prisma.garage.update({
      where: { id: garage.id },
      data: { xp: { increment: 5 }, likesReceived: { increment: 3 } },
    });
    expect(updated.xp).toBe(5);
    expect(updated.likesReceived).toBe(3);
  });

  it('accepts XpEvent rows for all 7 XpReason enum values', async () => {
    const { user } = await createUser({ email: 'xp3@jdm.test' });
    const garage = await garageFor(user.id);

    const reasons: XpReason[] = [
      'event_checkin',
      'car_create',
      'post_create',
      'post_like',
      'badge_award',
      'premium_activation',
      'admin_adjustment',
    ];
    for (const [i, reason] of reasons.entries()) {
      await prisma.xpEvent.create({
        data: {
          garageId: garage.id,
          delta: 1,
          reason,
          sourceRef: `seed:${reason}:${i}`,
        },
      });
    }
    const count = await prisma.xpEvent.count({ where: { garageId: garage.id } });
    expect(count).toBe(7);
  });

  it('rejects duplicate (garageId, reason, sourceRef) with P2002 (§C1 DB-enforced unique)', async () => {
    const { user } = await createUser({ email: 'xp4@jdm.test' });
    const garage = await garageFor(user.id);

    await prisma.xpEvent.create({
      data: {
        garageId: garage.id,
        delta: 1,
        reason: 'post_like',
        sourceRef: 'post:abc:reaction:r1',
      },
    });

    await expect(
      prisma.xpEvent.create({
        data: {
          garageId: garage.id,
          delta: 1,
          reason: 'post_like',
          sourceRef: 'post:abc:reaction:r1',
        },
      }),
    ).rejects.toMatchObject({ code: 'P2002' });
  });

  it('allows admin_adjustment with negative delta (sign rules are application-level)', async () => {
    const { user } = await createUser({ email: 'xp5@jdm.test' });
    const garage = await garageFor(user.id);
    const row = await prisma.xpEvent.create({
      data: {
        garageId: garage.id,
        delta: -50,
        reason: 'admin_adjustment',
        sourceRef: `admin:adm_1:${Date.now()}`,
      },
    });
    expect(row.delta).toBe(-50);
  });

  it('cascades XpEvent rows when Garage is deleted', async () => {
    const { user } = await createUser({ email: 'xp6@jdm.test' });
    const garage = await garageFor(user.id);
    await prisma.xpEvent.create({
      data: {
        garageId: garage.id,
        delta: 1,
        reason: 'event_checkin',
        sourceRef: 'event:e1',
      },
    });
    await prisma.garage.delete({ where: { id: garage.id } });
    const remaining = await prisma.xpEvent.count({ where: { garageId: garage.id } });
    expect(remaining).toBe(0);
  });

  it('raw SELECT confirms post-migration defaults are physically 0 on the column', async () => {
    // Schema contract: the `DEFAULT 0` clause on `xp` + `likesReceived` is
    // applied by Postgres at insert time (and by the ALTER TABLE for any
    // pre-existing rows in a prod-shape DB). Testcontainer Postgres starts
    // empty, so we cannot literally seed a row from a prior schema version;
    // instead we assert the post-migration default contract via a raw SELECT
    // that bypasses the Prisma client's default substitution and confirms the
    // underlying column values are physically 0. The prod-shape pre-existing
    // row path is covered transitively by the `DEFAULT 0` clause in the
    // generated migration SQL (Task 2.2 expected shape) — Postgres applies
    // that default during the `ALTER TABLE ADD COLUMN` to all existing rows.
    const { user } = await createUser({ email: 'xp7@jdm.test' });
    const garage = await garageFor(user.id);
    const rows = await prisma.$queryRaw<
      Array<{ xp: number; likesReceived: number }>
    >`SELECT "xp", "likesReceived" FROM "Garage" WHERE "id" = ${garage.id}`;
    expect(rows).toHaveLength(1);
    expect(rows[0]!.xp).toBe(0);
    expect(rows[0]!.likesReceived).toBe(0);
  });
});
```

Seven `it` blocks. Each one exercises a distinct contract: defaults, atomic increment, full enum coverage, DB-enforced unique (§C1), signed delta tolerance (forward-compat for §C8), FK cascade, raw-SQL default assertion (post-migration column-default contract).
