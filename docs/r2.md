# Cloudflare R2 — bucket CORS + lifecycle runbook

The mobile and admin clients PUT directly to R2 using a server-issued
presigned URL. R2 enforces CORS on the bucket; the API's
`CORS_ORIGINS` setting only controls the API's own CORS, **not** R2.

If browser uploads fail with:

```
Access to fetch at 'https://<account>.r2.cloudflarestorage.com/...' from origin
'https://<app>' has been blocked by CORS policy: Response to preflight request
doesn't pass access control check: No 'Access-Control-Allow-Origin' header is
present on the requested resource.
```

…the bucket CORS rules are missing or do not include the requesting origin.

## Canonical CORS spec

The canonical, repo-tracked CORS spec lives in `infra/r2-cors.json`. Apply it
to **every** bucket that receives presigned PUTs (prod + preview).

## Apply via Cloudflare dashboard

1. Cloudflare → R2 → select the bucket.
2. **Settings** → **CORS Policy** → **Add CORS policy** (or Edit).
3. Paste the contents of `infra/r2-cors.json`.
4. Save. Changes propagate within seconds.
5. Hard-reload the affected client and retry the upload.

## Apply via wrangler

```bash
# auth (one-time on the operator machine)
wrangler login

# apply
wrangler r2 bucket cors put <BUCKET_NAME> --rules infra/r2-cors.json

# verify
wrangler r2 bucket cors list <BUCKET_NAME>
```

Run once for the prod bucket and once for the preview bucket. Bucket names are
in `R2_BUCKET` (Railway service variables).

## Apply via S3 API (fallback)

Uses the `s3api put-bucket-cors` shape with R2's S3-compatible endpoint.

```bash
aws s3api put-bucket-cors \
  --endpoint-url "https://${R2_ACCOUNT_ID}.r2.cloudflarestorage.com" \
  --bucket "${R2_BUCKET}" \
  --cors-configuration "$(jq '{CORSRules: .}' infra/r2-cors.json)"
```

## Adding a new origin

Edit `infra/r2-cors.json`, open a PR, then re-apply with one of the methods
above. Do not edit dashboard rules in place without updating the file —
config drift will recur on the next bucket recreation.

## Verifying

After applying, run from the affected origin:

```bash
curl -i -X OPTIONS \
  -H 'Origin: https://<your-origin>' \
  -H 'Access-Control-Request-Method: PUT' \
  -H 'Access-Control-Request-Headers: content-type' \
  "https://<account>.r2.cloudflarestorage.com/<bucket>/probe"
```

Expect `HTTP/1.1 200` (or `204`) with `Access-Control-Allow-Origin` echoing
your origin and `Access-Control-Allow-Methods` containing `PUT`.

## Canonical lifecycle spec

The canonical lifecycle spec lives in `infra/r2-lifecycle.json`:

- `purge-orphan-uploads-24h`: objects under `orphan/` expire after 24h.
- `purge-deletion-tagged-objects-30d`: objects tagged `deletion-tag=true`
  expire after 30 days.

## Apply lifecycle via S3 API

```bash
aws s3api put-bucket-lifecycle-configuration \
  --endpoint-url "https://${R2_ACCOUNT_ID}.r2.cloudflarestorage.com" \
  --bucket "${R2_BUCKET}" \
  --lifecycle-configuration "$(cat infra/r2-lifecycle.json)"
```

Verify:

```bash
aws s3api get-bucket-lifecycle-configuration \
  --endpoint-url "https://${R2_ACCOUNT_ID}.r2.cloudflarestorage.com" \
  --bucket "${R2_BUCKET}"
```

Manual purge proof (operator runbook):

1. Upload a test object under `orphan/`.
2. Attach tag `deletion-tag=true` on a separate test object.
3. Confirm both objects are removed after their rule windows.

## Required API env vars for retention

| Variable                   | Default | Description                                                                            |
| -------------------------- | ------- | -------------------------------------------------------------------------------------- |
| `RETENTION_WORKER_ENABLED` | `false` | Enables the cron-based sweeper (runs daily at 02:00 BRT). Set to `true` in production. |
| `DELETION_GRACE_DAYS`      | `30`    | Days before a queued object is swept from R2.                                          |

When `RETENTION_WORKER_ENABLED=false`, the API falls back to immediate R2 deletion
at queue time. The queue row is written first (audit trail), then the object is
deleted and the row removed. If the immediate delete fails, the row persists for
manual or future-worker sweep.

**Production checklist**: set `RETENTION_WORKER_ENABLED=true` on the Railway API
service so the scheduled sweeper handles bulk and retry scenarios.

## Bucket privado de documentos

Documento de identidade NÃO vai para o bucket principal. O principal é
legível através de `R2_PUBLIC_BASE_URL`, e um `objectKey` com cuid2 é difícil
de adivinhar, não um controle de acesso.

Criar um bucket separado:

- Sem dev subdomain público: `r2.dev` desabilitado.
- Sem custom domain.
- Sem política de leitura pública.
- Mesma credencial de API do bucket principal, ou uma credencial própria com
  escopo só nele.

Setar `R2_DOCUMENTS_BUCKET` com o nome dele. Se o R2 está configurado e essa
variável está ausente ou vazia, `buildUploads` lança um erro e a API não
sobe. Isso é proposital. Assim um documento de identidade nunca cai em
silêncio no bucket público. O fallback para `R2_BUCKET` só vale para
`DevUploads`, em desenvolvimento local e em testes.

Leitura sempre por signed GET com TTL de `DOCUMENT_URL_TTL_SECONDS`, default
60 segundos. Nunca usar `buildPublicUrl`.
